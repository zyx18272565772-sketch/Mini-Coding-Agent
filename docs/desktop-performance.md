# 长会话输入与发送性能

## 问题与处理

Windows 使用 `spawn` 启动任务进程。将完整消息历史放进进程参数时，`Process.start()` 需要把参数写进启动管道；历史超过管道缓冲后，会等待新解释器完成导入并读取数据。发送接口因此随历史增长而变慢。现在启动参数保持很小，工作进程先发送 `worker_ready`，再接收完整任务数据。后台接收线程负责传输，传输期间不持有桌面服务锁；模型收到的历史内容保持完整。

输入草稿、状态轮询都会使 React 父组件更新。历史 Markdown 的正文没有变化时，`MessageContent` 使用 `React.memo` 跳过重复解析与语法高亮；空轮询复用事件数组，避免重新构建时间线。新的流式文字仍正常更新，不缓存过期正文。主题、字号、复制和引用功能继续生效。

点击发送后立即显示临时消息与“正在发送”状态，不等待进程准备完成。后端正式用户事件出现后不再显示临时消息；失败时保留草稿和引用，不把临时消息写入模型历史。等待确认期间禁止重复提交，输入框仍可以编辑下一段内容，后续确认不会清除已经修改的草稿。

## 本机测量记录

日期：2026-10-22。Windows、Python 3.12、项目虚拟环境、生产构建页面、独立无头 Chrome。模型与远程工具均为模拟调用；不使用真实令牌或付费模型。测量只复制原会话到临时数据目录，不改写用户会话。

| 测量项 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 空会话提交接口，3 次中位数 | 10.89 ms | 12.00 ms |
| 已有会话提交接口，3 次中位数 | 1311.69 ms | 19.03 ms |
| 长会话连续输入 11 个字符的脚本时间，3 次中位数 | 752.8 ms | 17.6 ms |
| 长会话空轮询 1.6 秒内的脚本时间 | 193.3 ms | 7.0 ms |
| 后端人为延迟 1.8 秒时，点击至显示用户消息 | 1971 ms | 38 ms |

后端已有会话样本为 44 条模型消息、165 条界面事件，JSON 文件约 287 KB。浏览器固定样本为 24 轮对话，每个回复包含表格和 18 个 Python 函数的代码块；通过 CDP `Performance.getMetrics` 的 `ScriptDuration` 测量脚本累计执行时间。输入测量不是单个按键的 INP。最后一项是即时反馈改善，不代表模型请求或后端执行已在 38 ms 内完成。实际桌面环境和调试器会影响耗时。

## 回归验证

- `tests/test_desktop_send.py`：握手后接收历史、断开时退出、传输长历史时桌面服务锁可用。
- `frontend/src/state.test.js`：空事件保持数组引用，但仍接收新的状态和项目任务。
- `tests/desktop_send_ui.cjs`：真实 Chrome 输入与轮询测量、模拟慢提交、确认去重、失败保留新草稿；默认要求消息反馈小于 600 ms、每组输入脚本时间小于 300 ms。
- 原有浏览器验收继续检查附件与引用、流式输出、停止及失败后继续。

浏览器脚本使用 `tests/desktop_browser_server.py` 的临时本机服务，默认地址为 `http://127.0.0.1:9011/`。`PLAYWRIGHT_MODULE` 可指向已有 Playwright 安装，`DESKTOP_TEST_URL` 可覆盖测试服务地址。`PERF_BASELINE=1` 仅记录基线、跳过性能门限；正常回归不设置此变量。测量 JSON 与截图写入被 Git 忽略的 `.agent_data/ui-checks/`。
